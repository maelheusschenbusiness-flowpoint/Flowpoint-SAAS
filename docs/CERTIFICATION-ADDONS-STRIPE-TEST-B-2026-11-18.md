## Défauts (preuves)
* **D1 — Haut, bêta/migration : table `seo_change_impact_settings` absente de la base de test.** `information_schema` : seules `audits` et `conversion_opportunity_settings` existent parmi les tables des add-ons récents (`seo_change_impact_settings`, `local_landing_opportunity_settings`, `agency_portfolio_priority_settings`, `technical_seo_fix_verifications` absentes). Cause : `initDataTables` crée ces tables dans le bloc gardé par le marqueur `missing-production-tables-v3` (src/services/init-data-tables.ts ~l.3371) ; une base ayant déjà enregistré v3 ne les reçoit jamais (même mécanisme que `competitor_map_results`, corrigé par un « self-heal » hors marqueur). La base de production peut être concernée : à vérifier. Correction suggérée : un `CREATE TABLE IF NOT EXISTS` toujours exécuté, comme `ensureGbpPerformanceSettingsSchema`.
* **D2 — Haut (probablement aussi en production, code identique) : l'abonnement d'add-on écrase l'identifiant d'abonnement de l'organisation.** `customer.subscription.created/updated` d'un abonnement `addonSub` écrit `organizations.stripe_subscription_id`, `subscription_status` (`trialing`→`active`) et la période (routes/stripe-webhook.ts ~l.2340) : l'organisation `815b117b…` pointe vers `sub_1UdZ1r…` (add-on) au lieu de l'abonnement Pro. Conséquence directe : `POST /api/addons/:key/deactivate` tente de supprimer le dernier élément de l'abonnement d'add-on (« A subscription must have at least one active plan », addon-stripe-sync.ts:324) → 502, le client ne peut pas résilier l'add-on ; les opérations de plan visent le mauvais abonnement. Correction : ignorer les écritures de plan quand `metadata.addonSub` est posé et qu'aucun prix de plan n'est présent.
* **D3 — Moyen (TEST seulement) : le webhook ne retire pas le droit d'un add-on dont le prix n'existe qu'en TEST.** `persistAddonsFromSubscription` (stripe-webhook.ts ~l.501) fait `if (!APIDS[key]) continue;` avec `ADDON_PRICE_IDS` (catalogue LIVE, vide pour ces deux add-ons) : jamais désactivés par la réconciliation. Constaté : `org_addons.active=true` et API 200 après `customer.subscription.deleted` de l'abonnement d'add-on. Correction : tenir compte de `ADDON_PRICE_IDS_TEST`.
* **D4 — Haut : course à l'activation.** Deux `activate` simultanés créent deux abonnements d'add-on (la recherche de l'abonnement d'add-on et la création ne sont pas atomiques : addon-stripe-sync.ts `findOrCreateAddonSubscription`, aucune clé d'idempotence ni verrou). Le client est débité deux fois (15 EUR × 2) ; `org_addons.quantity` passe à 2. Un rejeu séquentiel est correct (`already_on_subscription`, vérifié sur Conversion).
* Observations : l'add-on est facturé immédiatement pendant l'essai du plan (abonnement séparé sans essai) ; `orgId` des abonnements de plan = e-mail (défaut 2 de la phase 1, inchangé) ; bruit 500 `/api/google/reviews` dans les journaux des parcours locaux (Google non connecté, sans effet sur les tests).
